## 第 3 頁｜Repo 記錄中的三個迭代

**講者：B｜約 50 秒**

從 repo 可以看出三個階段。十月初先有規格和專案骨架；十月十七日 F1 自動化測試到 101 項；Iteration 1 收尾時到 112 項；十一月八日 PR 34 合併後，GitHub main 記錄 157 項測試通過。我們不把測試數當成唯一 KPI，但它能證明 AI 提出的修改有被落實並接受回歸驗證。真正完整的證據要把需求、commit 或 PR、測試結果三者放在一起看。

## 第 4 頁｜AI 協作流程落在 GitHub 上

**講者：B｜約 50 秒**

我們把 AI 協作固定成五步。先用需求或缺陷定義問題，再請 AI 枚舉邊界情況或草擬修改；接著由人判斷資料模型、錯誤碼和相容性；測試要先能重現問題，再修到通過；最後透過 PR 讓非作者 review。這個流程的價值是每一步都有證據：週報裡有缺陷編號，commit 能定位變更，測試能驗收，PR 則保留討論與整合脈絡。

## 第 5 頁｜案例一：資料格式重構後，AI 建議要經過測試

**講者：B｜約 60 秒**

第一個案例是資料儲存格式重構。Storage 已經改成每個 ID 一個檔案，但舊測試仍在讀整包 JSON，所以一次出現 22 個錯誤。AI 可以很快協助定位是哪一組測試與資料路徑失配，但是否回到舊格式，不能交給 AI 決定。我們依照架構文件確認 per-ID 才是目標 schema，接著更新測試，補上舊資料與損毀紀錄的邊界情況，最後跑完整回歸。這次經驗是：AI 的修法必須服從團隊已確認的資料契約。

## 第 6 頁｜案例二：F2 / F3 review 抓到跨模組錯位

**講者：C｜約 65 秒**

第二個案例是 F2 與 F3 的跨模組 review。AI 對照需求時，先指出重複加選不應該被誤報成課程衝堂，也提醒欄位命名和資料來源可能不一致。實際檢查後，我們找到 F3 使用 type、student_ids，但專案共同模型是 course_type、enrolled_courses；活動選課也一度同時寫在兩個地方。這些建議不是全部照單全收，例如 AI 曾認為活動衝堂機制無效，但我們檢查程式後發現活動本來就被建模成課程，因此拒絕那項判斷。最後透過 PR 34 和 157 項測試驗收。

## 第 7 頁｜案例三：F 的本地品質補強

**講者：F｜約 65 秒**

第三個案例是我在本地完成的 F4 品質補強。這裡特別把 GitHub main 的 157 項，和本地新增的 20 項分開呈現；本機目前可以跑到 177 項，但 commit 91a0bb9 還沒有 push，也還沒經過 PR review，所以不能宣稱是團隊已合併成果。這 20 項主要檢查空白標題、容量、設備需求、教室衝堂，以及失敗時不能留下半套狀態。下一步要先推 branch、開 PR，再由非作者 review，完成後才更新正式數字。

## 第 8 頁｜AI 有效的地方，以及不能外包的責任

**講者：E｜約 55 秒**

綜合前面的紀錄，AI 最有效的是快速枚舉邊界條件、草擬測試與重構、比對文件，以及在 review 時提示跨檔案不一致。但四件事不能外包：共同 schema、驗收語言、接受或拒絕建議的決策，以及實際執行測試與 merge 的證據。我接下來負責 F9、F10 時，也會先由團隊定義路徑與動態重排的不變條件，再用 AI 產生候選案例和實作，最後仍以測試與 PR 驗收。

## 第 9 頁｜五人團隊下一階段的 AI 協作規則

**講者：F｜約 45 秒**

最後，我們把心得整理成五條規則。Prompt 必須連到需求或缺陷；PR 前大家跑同一套測試；AI 草擬者不能是唯一驗收者；D 退選後，F3、F4 要重新交接；我的本地 F4 則先完成 push 和 PR，讓 177 項測試成為可驗證的團隊成果。對我們來說，AI 讓提出答案更快，而 GitHub、測試與 review，才讓答案值得被團隊相信。謝謝大家。
