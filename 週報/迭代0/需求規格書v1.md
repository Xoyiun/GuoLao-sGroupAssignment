# 需求規格書 v1 

## 模組編號：F1 課程與學生資料管理

### 1. 功能概述
本模組提供系統基礎資料之管理介面，支援課程資料與學生基本資料的新增、修改、刪除與多條件查詢功能 [4]。所有功能必須透過自行設計之函式實作，嚴禁使用全域變數傳遞資料 [2]。

### 2. 輸入資料規格 (Input)
* **課程資料 (Course)**：
  * `course_id` (String)：課程代號（格式：2碼英文字母 + 3碼數字，如 `CS101`），必須唯一且不可重複 [4]。
  * `title` (String)：課程名稱（如 `計算機程式設計`）。
  * `credits` (Int)：學分，必須為正整數 (\\(> 0\\)) [4]。
  * `required` (Bool/Enum)：必選修類別（`必修` 或 `選修`）[4]。
  * `teacher` (String)：授課教師姓名 [4]。
  * `capacity` (Int)：修課人數上限，必須大於或等於 1 [4]。
  * `classroom` (String)：授課教室代號（如 `TR-310`）[4]。
  * `time_slots` (List of Objects)：上課時段清單。
    * 星期：以整數 `1–7` 表示（1 表示星期一，7 表示星期日）[4]。
    * 節次：以字串 `1–9`、`a`、`b`、`c` 表示 [4]。
* **學生資料 (Student)**：
  * `student_id` (String)：學號（格式：1碼大寫英文字母 + 8碼數字，如 `S11200001`），必須唯一且不可重複 [4]。
  * `name` (String)：學生姓名 [4]。
  * `department` (String)：系級 [4]。
  * `enrolled_courses` (List of Strings)：已選課程代號清單 [4]。
  * `max_credits` (Int)：學分上限（預設 25，必須為正整數）[4]。

### 3. 處理規則與商業邏輯 (Processing Rules)
1. **唯一性檢查**：新增課程或學生時，若 `course_id` 或 `student_id` 已存在，系統須拒絕新增並印出錯誤提示 [4]。
2. **數值與格式驗證**：
   * 學分小於等於 0 或容量小於 1 時拒絕建立 [4]。
   * 節次輸入非 `1–9, a, b, c` 範圍時，判定為非法節次並提示錯誤 [4, 5]。
3. **刪除防護機制**：若某門課程的已選人數 \\(> 0\\)（即已有學生選修），系統**嚴禁直接刪除該課程**；必須要求先執行退選或課程取消程序 [4]。
4. **多條件查詢支援**：系統需支援依據「課程代號」、「授課教師」、「星期時段」、「必選修」及「剩餘名額 (\\(>0\\))」單一或複合條件進行查詢 [4]。
5. **錯誤處理與容錯**：遇到無效輸入時，系統需印出對應錯誤提示，**不得導致程式異常終止 (Crash)** [2, 6]。

### 4. 輸出結果範例 (Output Example)
* **新增成功**：
  `[成功] 課程 [CS101] 計算機程式設計 新增成功。`
* **新增失敗（代號重複）**：
  `[錯誤] 新增失敗：課程代號 CS101 已重複存在。`
* **刪除失敗（已有學生選修）**：
  `[錯誤] 刪除失敗：課程 CS101 目前已有 3 名學生選修，請先辦理退選。`

### 5. 驗收條件 (Acceptance Criteria)
* 系統必須預設載入或建立至少 **20 門課程**、**15 名學生** 及 **5 間教室** 的測試資料 [5]。
* 系統必須通過單元測試，驗證能正確拒絕重複代號、非法節次（如節次輸入 `d` 或 `0`）及無效學分 [5]。

## 模組編號：F2 多層次衝堂與選課檢查

### 1. 功能概述
本模組提供學生選課時的多重條件檢查機制，防止學生發生課程衝堂、活動時間衝突、教室空間衝突、學分超修或選修額滿課程等情況。此模組設計之核心為全域與多面向驗證，不得使用停跳（Early Break）機制僅印出第一項錯誤。

### 2. 輸入資料規格 (Input)
* `student_id` (String)：進行加選之學生學號（如 `S11200001`）。
* `course_id` (String)：預計加選之目標課程代號（如 `CS102`）。
* `current_enrolled_courses` (List of Objects)：該學生已選課程清單及對應之時段資料。
* `current_activities` (List of Objects)：該學生已參加之校園活動與對應時段資料。
* `classroom_schedules` (List of Objects)：各教室之時間佔用資料。

### 3. 處理規則與商業邏輯 (Processing Rules)
1. **多重條件完整掃描**：進行選課檢查時，系統必須依序掃描所有條件（學生衝堂、教室衝堂、活動衝突、學分上限、人數上限），將發現的所有衝突紀錄於列表中，最後統一回傳結果，**嚴禁在發現第一個衝突時即中斷檢查**。
2. **學生時段衝堂檢查**：比較欲加選課程之 `time_slots` 與學生已選課程之 `time_slots`，若有任何一節次重疊即判定為衝堂。
3. **活動時間衝突檢查**：比較欲加選課程之 `time_slots` 與學生已報名活動之時間，若有重疊即記錄衝突活動名稱與時間。
4. **教室衝突檢查**：檢查目標課程所使用之教室於該上課時段是否已安排其他課程或活動。
5. **學分上限驗證**：計算 `目前已選學分 + 加選課程學分`，若大於學生之 `max_credits`，記錄學分超修衝突。
6. **名額限制驗證**：若該課程之已選人數已達到 `capacity` 上限，記錄課程已額滿訊息。
7. **排序規則**：若發現多項衝突，輸出時必須**依據星期（星期一至星期日）及節次順序**遞增排序呈現。

### 4. 輸出結果範例 (Output Example)
```text
學生：S11200001
欲加選：CS102 Python 程式設計
選課結果：失敗
衝突 1：星期二第 3、4 節
已選課程：MA101 微積分
衝突 2：星期四第 5 節
已參加活動：程式設計讀書會
目前學分：18
加選後學分：21
學分上限：24
```

## 模組編號：F3 個人課表產生與空閒時段查詢

### 1. 功能概述
本模組負責將學生已選取之課程與已報名之校園活動資料，彙整並轉換為每週 7 天 × 12 節次之二維課表矩陣。同時提供課表多維度查詢、連續空閒時段搜尋以及每日與每週之課表數據統計功能。

### 2. 輸入資料規格 (Input)
* `student_id` (String)：欲查詢之學生學號（如 `S11200001`）。
* `query_type` (Enum)：查詢模式（`全表顯示`、`依星期/節次`、`依課程代號`、`空閒時段搜尋`）。
* `time_range` (Object, 選填)：空閒時段查詢之指定區間（如：星期一至星期三，第 1–5 節）。
* `min_free_slots` (Int, 選填)：連續空閒節數需求（如：預設至少連續 3 節空堂）。

### 3. 處理規則與商業邏輯 (Processing Rules)
1. **二維課表矩陣建置**：以列（Row）為節次（第 1–12 節）、欄（Column）為星期（星期一至星期日，共 7 天）建立 12×7 之矩陣結構 [1]。
2. **多時段與活動映射**：
   * 若單一課程每週有多次上課時段（如星期二 3,4 節與星期四 5 節），必須在矩陣對應之所有位置正確填入課程名稱與教室 [1]。
   * 活動（如讀書會、講座）需與課程一同填入課表矩陣，並標註類型。
3. **數據統計計算**：
   * **每日上課節數**：加總該日所有課程與活動佔用之總節數 [1]。
   * **每週總學分**：統計該學生所有已選課程之 `credits` 總和 [1]。
   * **總空堂數**：計算每日第一堂課與最後一堂課之間的未佔用節數（間隔空堂） [1]。
4. **連續空閒時段搜尋算法**：掃描指定時間區間內未被課程或活動佔用之連續時段，若連續長度 \\(\ge \text{min\_free\_slots}\\)，則將該時段列入可用清單輸出 [1]。

### 4. 輸出結果範例 (Output Example)
```text
學生：S11200001 (總學分：18，每週空堂數：5 節)
=================== 每週個人課表 (12x7) ===================
節次 \ 星期 | 星期一 | 星期二 | 星期三 | 星期四 | 星期五 | ...
-----------------------------------------------------------
第 1 節    |        |        |        |        |        |
第 2 節    | CS101  |        | CS101  |        |        |
第 3 節    | CS101  | MA101  | CS101  |        |        |
第 4 節    |        | MA101  |        |        |        |
第 5 節    |        |        |        | 讀書會  |        |
...
-----------------------------------------------------------
[統計資訊]
- 每日上課節數：一(3節)、二(2節)、三(3節)、四(1節活動)、五(0節)
- 連續空閒時段查詢 (條件：至少連續 3 節)：
  1. 星期二 第 5–8 節 (連續 4 節空閒)
  2. 星期五 第 1–12 節 (整天空閒)
```

## 模組編號：F4 校園活動與教室配置

### 1. 功能概述
本模組負責校園非課程活動（如社團活動、讀書會、講座等）之管理與教室資源配置。系統能根據活動之時間、預計人數與設備需求，自動篩選並配置合適場地，並與 F1 課程及 F2 衝堂檢查共用相同的時段衝突檢查機制。

### 2. 輸入資料規格 (Input)
* `activity_id` (String)：活動代號（如 `ACT001`），必須唯一且不可重複。
* `title` (String)：活動名稱（如 `Python 程式設計讀書會`）。
* `date` (String)：活動日期或每週星期（如 `星期四` 或 `2026-10-15`）。
* `time_slots` (List of Objects)：活動佔用時段（以星期 1–7 與節次 1–9, a, b, c 表示）。
* `expected_participants` (Int)：預計參加人數（必須為正整數）。
* `activity_type` (String)：活動類型（如 `學術講座`、`社團社課`、`會議`）。
* `required_equipment` (List of Strings)：場地設備需求（如 `投影機`、`麥克風`、`電腦`）。
* `assigned_classroom` (String, 可空)：已配置之教室代號。

### 3. 處理規則與商業邏輯 (Processing Rules)
1. **活動生命週期管理**：支援活動的新增、資料修改、取消（刪除）與關鍵字查詢功能。
2. **自動場地篩選邏輯**：
   * 系統須比對各教室之容納人數 (`capacity >= expected_participants`)。
   * 比對教室之設備清單是否涵蓋 `required_equipment`。
   * 比對該教室於活動時段內是否已被其他課程或活動佔用（與 F1/F2 時段衝突檢查機制共用）。
3. **無合適場地之錯誤處理**：若無法找到符合條件之教室，系統不得直接崩潰，須精準輸出「未滿足之條件」（例如：`原因：無可容納 50 人且包含投影機之空閒教室`）。
4. **報名人數上限控管**：報名參加活動之學生人數，不得超過該活動設定之 `expected_participants`，亦不得超過所配置教室之容量上限。
5. **教室獨佔性約束**：同一間教室在相同星期與節次，嚴禁重複配置給兩個（含）以上之活動或課程。

### 4. 輸出結果範例 (Output Example)
```text
[成功] 活動 [ACT001] Python 讀書會 建立成功。
分配教室：TR-310 (容量：60 人，設備：投影機、麥克風)
預計人數：20 人
佔用時段：星期四 第 5 節

[失敗] 活動 [ACT002] 大型演講 建立失敗。
原因：無法配置教室（未滿足條件：需要容量 >= 150 人且具備麥克風之空閒教室）。
```

## 模組編號：F5 多條件課程篩選與可行性檢查

### 1. 功能概述
本模組提供學生彈性設定個人選課條件與限制（包含必修課程、學分上下限、不可上課時段與偏好上課星期），系統能自動從所有課程中進行條件過濾與可行性判斷，篩選出符合條件之候選課程清單，並在條件矛盾或無法滿足時給出明確警示。

### 2. 輸入資料規格 (Input)
* `student_id` (String)：學生學號（如 `S11200001`）。
* `mandatory_courses` (List of Strings)：必修課程代號清單（如 `["CS101", "MA101"]`）。
* `preferred_courses` (List of Strings)：希望修習之選修偏好課程清單。
* `min_credits` (Int)：期望選修之最低學分（必須 \\(\ge 0\\)）。
* `max_credits` (Int)：期望選修之最高學分（不得超過學生之學分上限）。
* `forbidden_time_slots` (List of Objects)：不可上課時段清單（例如：星期五第 8、9 節不排課）。
* `preferred_days` (List of Int)：偏好上課星期清單（例如：`[2-4]` 代表偏好一、二、三）。

### 3. 處理規則與商業邏輯 (Processing Rules)
1. **硬性限制過濾 (Hard Constraints)**：
   * **禁止時段排除**：若某門課程的上課時段包含於 `forbidden_time_slots` 中，系統須自動將該課程自候選清單中剔除（若該課為必修，則觸發「條件衝突」警示）。
   * **額滿課程排除**：若課程之已選人數已達 `capacity` 上限，直接列為不可選候選課。
2. **軟性偏好篩選 (Soft Preferences)**：
   * 優先標記符合 `preferred_days` 與 `preferred_courses` 之課程。
3. **學分可行性檢查 (Feasibility Check)**：
   * **無法滿足最低學分**：若所有可用候選課程（含必修）之學分總和仍低於 `min_credits`，輸出「無法滿足最低學分」警示。
   * **必修學分即超修**：若僅計算 `mandatory_courses` 之總學分就已超過 `max_credits`，輸出「必修學分超過上限」警示。
4. **矛盾條件偵測**：若輸入條件彼此衝突（例如：必修課開在不可上課時段，或必修課已額滿），系統須精準說明衝突原因，不得靜默失敗。

### 4. 輸出結果範例 (Output Example)
```text
[檢查結果] 選課可行性判斷：失敗 (發現 2 項條件衝突)
===========================================================
- 衝突 1 [條件矛盾]：必修課 MA101 (星期五 8,9 節) 落在您設定的「不可上課時段」。
- 衝突 2 [無法滿足最低學分]：排除衝突與額滿課程後，剩餘可行課程最高總學分為 12，低於您設定的最低學分需求 (15 學分)。

[候選課程篩選清單]
- CS101 計算機程式設計 (3 學分) [必修] - 符合
- ENG101 大一英文 (2 學分) [符合偏好星期] - 符合
```

## 模組編號：F6 資料儲存與系統測試

### 1. 功能概述
本模組負責全系統所有資料（包含課程、學生、教室、活動及選課紀錄）之持久化儲存與自動載入機制，採用 JSON 或 CSV 格式進行檔案讀寫。此外，本模組定義了系統之防禦性程式設計原則與自動化測試規範，確保系統重新啟動後能完整恢復狀態，且具備單筆資料格式錯誤之容錯能力。

### 2. 輸入資料規格 (Input)
* **資料檔案**：
  * `courses.json` / `courses.csv`：課程基本資料與上課時段。
  * `students.json` / `students.csv`：學生資料、已選課程與個人學分上限。
  * `classrooms.json` / `classrooms.csv`：教室基本資料與場地設備。
  * `activities.json` / `activities.csv`：校園活動資料與場地配置。
  * `enrollments.json` / `enrollments.csv`：選課與報名歷史紀錄。
* **自動化測試案例輸入**：測試框架專用之擬真測試資料集。

### 3. 處理規則與商業邏輯 (Processing Rules)
1. **資料持久化儲存 (Persistence)**：當進行資料異動（如新增課程、學生選課、取消活動）時，系統需將最新狀態寫入對應之 CSV/JSON 檔案中。
2. **啟動載入與格式驗證 (Load & Validation)**：
   * 程式啟動時，自動讀取儲存檔案並還原記憶體資料結構。
   * **防禦性錯誤處理**：逐筆檢查欄位型態與格式。若遇到單筆資料損毀或格式不符（如學分為字串、節次非法），系統須跳過該筆不良紀錄或載入預設值並發出警示，**嚴禁導致整個系統中斷崩潰 (Crash)**。
3. **自動化測試集架構 (Automated Test Suite)**：
   * 建立不依賴人工鍵盤輸入之獨立測試函式。
   * 測試案例總數不得少於 30 個，並劃分為三大類：
     1. **正常案例 (>= 10 個)**：驗證合法資料之新增、修改、查詢與正常選課流程。
     2. **邊界案例 (>= 10 個)**：驗證學分剛好等於上限、人數剛好額滿、節次介於邊界（如第 1 節或 c 節）、連續空堂邊界等情境。
     3. **錯誤與衝突案例 (>= 10 個)**：驗證重複代號、時間衝堂、教室衝突、檔案格式損毀及超修拒絕等情境。

### 4. 輸出結果範例 (Output Example)
```text
[系統啟動] 正在載入資料庫檔案...
- 載入 courses.json：成功 (共 20 門課程)
```

## 模組編號：F7 多條件最佳課表搜尋

### 1. 功能概述
本模組負責針對學生設定之必修課、候選選修課與多重限制條件，自動搜尋出所有符合硬性約束之「可行課表組合」，並透過團隊自訂之量化評分函式（對各項軟性偏好給予加權計分），將可行課表依推薦分數由高至低進行排序輸出。

### 2. 輸入資料規格 (Input)
* `student_id` (String)：進行課表搜尋之學生學號（如 `S11200001`）。
* `mandatory_courses` (List of Strings)：必修課程代號清單（必須全部納入）。
* `candidate_courses` (List of Strings)：可供選擇之候選選修課代號清單。
* `credit_bounds` (Object)：學分上下限（`min_credits` 與 `max_credits`）。
* `forbidden_time_slots` (List of Objects)：不可上課之禁止時段。
* `preference_weights` (Object)：偏好條件權重設定（權重總和為 1.0 或 100 分）：
  * `weight_min_days` (Float)：減少到校天數之權重。
  * `weight_min_gaps` (Float)：減少空堂節數之權重。
  * `weight_no_early_8am` (Float)：避免早八課程（第 1 節）之權重。
  * `weight_concentrated` (Float)：集中上課時段之權重。
  * `weight_preferred_ratio` (Float)：偏好選修課命中比例之權重。

### 3. 處理規則與商業邏輯 (Processing Rules)
1. **硬性限制嚴格過濾 (Hard Constraints)**：
   產生的每組候選課表必須 100% 滿足以下 5 項條件，否則直接判定為無效課表並予以剔除：
   * **必修全含**：`mandatory_courses` 中的所有課程必須全部包含在內。
   * **無衝堂**：課表內任意兩門課程的上課時段完全無重疊。
   * **學分合規**：`min_credits <= 總學分 <= max_credits`。
   * **無額滿課**：不得選擇 `capacity` 已滿之課程。
   * **無禁止時段**：所有課程時間均不得落入 `forbidden_time_slots`。

2. **軟性偏好量化評分公式 (Soft Preference Scoring)**：
   對每一組符合硬性限制的可行課表算出一總評分（Score），公式定義如下：
   \\[\text{Total Score} = (w_1 \times S_{\text{days}}) + (w_2 \times S_{\text{gaps}}) + (w_3 \times S_{\text{no\_8am}}) + (w_4 \times S_{\text{conc}}) + (w_5 \times S_{\text{pref}})\\]
   * **到校天數分數 (\\(S_{\text{days}}\\))**：有課天數越少得分越高。
   * **空堂分數 (\\(S_{\text{gaps}}\\))**：每日首堂與尾堂間之空堂總節數越少得分越高。
   * **非早八分數 (\\(S_{\text{no\_8am}}\\))**：未排在第 1 節之課程比例越高得分越高。
   * **時段集中度 (\\(S_{\text{conc}}\\))**：上課時間越集中（如全排上午或全排下午）得分越高。
   * **偏好命中率 (\\(S_{\text{pref}}\\))**：選入之選修課包含學生偏好清單之比例越高得分越高。

3. **排序與結果輸出**：
   計算完所有可行課表之評分後，依總分數進行降冪排序（由高至低），並輸出前 \\(N\\) 組最佳推薦課表。

### 4. 輸出結果範例 (Output Example)
```text
搜尋完成！共找到 12 組可行課表組合（已依偏好評分排序）：

【推薦第 1 名】總評分：92.5 分 (預估總學分：18)
- 課程清單：CS101(必), MA101(必), ENG102(選), CS201(選)
- 評分明細：
  * 到校天數：3 天 (得分: 95)
  * 空堂節數：共 1 節 (得分: 90)
  * 早八課程：0 門 (得分: 100)
  * 偏好選修命中率：100% (得分: 100)

【推薦第 2 名】總評分：84.0 分 (預估總學分：17)
- 課程清單：CS101(必), MA101(必), ENG102(選), HIS101(選)
- 評分明細：到校 4 天、空堂 3 節、早八 1 門...
```

### 5. 驗收條件 (Acceptance Criteria)
* 系統必須搜尋並列舉出「所有」滿足 5 大硬性條件的可行課表組合。
* 評分機制必須能明確呈現不同權重設定（例如調整「到校天數」權重最高 vs 「避免早八」權重最高）對課表推薦排序結果之實質影響。
* 當硬性條件矛盾（如必修課數量已導致無法避開早八或無可行組合）時，能給出明確的未滿足原因說明。

## 模組編號：F8 搜尋演算法比較 (Search Algorithm Comparison)

### 1. 功能概述
本模組針對 F7 所定義之課表搜尋問題，實作 **窮舉搜尋 (Brute Force / Exhaustive Search)** 與 **回溯搜尋 (Backtracking Search)** 兩種不同的演算法，藉由記錄搜尋節點數、執行時間與可行解數量進行量化效能比較。同時驗證兩者在相同輸入下解集的一致性，並觀察候選課程規模擴大時之時間複雜度變化。

### 2. 輸入資料規格 (Input)
* `candidate_courses` (List of Objects)：候選課程清單（至少準備包含 8 門、12 門、16 門課程之三組測試集）。
* `mandatory_courses` (List of Objects)：必修課程清單。
* `hard_constraints` (Object)：硬性約束條件（含衝堂判斷、學分上下限、教室與禁止時段）。
* `timeout_limit` (Int)：窮舉法執行時間上限（預設例如 30 秒，避免極端規模導致程式卡死）。

### 3. 處理規則與商業邏輯 (Processing Rules)
1. **窮舉搜尋演算法 (Exhaustive Search)**：
   * 產生所有可能的候選課程組合（\\(2^N\\) 種狀態空間組合）。
   * 對每一個組合完整掃描 5 大硬性限制條件，若通過則放入可行解集合。
   * 記錄總檢查組合數（搜尋節點數）與總執行時間。
2. **回溯搜尋演算法 (Backtracking Search)**：
   * 採用樹狀狀態空間展開，在排課過程中實施**剪枝策略 (Pruning)**（例如：一旦發現當前加選的課程與先前已選課程衝堂，即刻回溯，不再展開該分支）。
   * 記錄走訪之搜尋節點數與總執行時間。
3. **結果一致性交集檢查 (Consistency Check)**：
   * 自動比對窮舉法與回溯法產出的可行解集合，確認兩者找到的可行課表數量與內容 **100% 完全相同**。
4. **超時防禦機制 (Timeout Mechanism)**：
   * 若窮舉法在規定時間上限（如 30 秒）內無法執行完畢，系統須強制中斷，印出 `[Timeout]` 警示並如實記錄已搜尋之節點數與「未完成」狀態，不得造成系統 Crash。

### 4. 輸出結果範例 (Output Example)
```text

[測試集 1：候選課程 N = 8 門]

- 回溯搜尋 (Backtracking): 搜尋節點 32 個  | 耗時 0.001 秒 | 可行解 4 組
- 解集一致性檢查       : [PASS] 兩者可行解集合完全相同。

- 回溯搜尋 (Backtracking): 搜尋節點 128 個  | 耗時 0.008 秒 | 可行解 12 組
```

### 5. 驗收條件 (Acceptance Criteria)
* 系統必須建立包含 **8 門、12 門及 16 門** 候選課程之三組實驗測試案例 [1]。
* 驗證在未超時狀況下，窮舉法與回溯法產出的可行解數量與結果完全一致 [1]。
* 針對窮舉法設定合理時間上限，超時時能正確擷取未完成狀態並輸出實驗日誌 [1]。
* 能夠繪製或輸出兩演算法隨著 \\(N\\) 增加時「搜尋節點數」與「執行時間」之差異數據

## 模組編號：F9 校園移動路徑規劃 (Campus Path Planning)

### 1. 功能概述
本模組建立校園建築物與步行路徑之圖形資料結構（Graph），實作 Dijkstra / BFS 演算法以計算任意兩建築物（教室）間的最短移動路徑與所需步行時間。此模組將與 F2 / F7 課表可行性檢查機制整合，確保學生連續兩節課之間的轉場時間不超過實際空堂間隔。

### 2. 輸入資料規格 (Input)
* `campus_graph` (Object)：校園地圖圖形資料。
  * `nodes` (List of Objects)：至少 10 個建築物節點（如 `TR` 研揚大樓、`E2` 工程二館、`MA` 管理大樓等）。
  * `edges` (List of Objects)：至少 15 條邊（包含起點、終點與預估步行時間分秒）。
* `start_location` (String)：起點建築物/教室代號（如 `TR-310`，可自動對應至 `TR` 節點）。
* `end_location` (String)：終點建築物/教室代號（如 `MA-101`，可自動對應至 `MA` 節點）。
* `available_gap_minutes` (Int)：兩堂課之間的離堂/空堂時間（如 10 分鐘）。

### 3. 處理規則與商業邏輯 (Processing Rules)
1. **地圖圖形資料結構建置**：
   * 以鄰接串列（Adjacency List）或鄰接矩陣（Adjacency Matrix）表示校園地圖，確保包含至少 10 個建築物節點與 15 條邊。
2. **最短路徑與時間計算**：
   * **Dijkstra 演算法**：針對不同路線具備不同權重（步行時間）之情況，計算起點至終點之全域最短時間與最佳移動路線。
   * **BFS 演算法**：當所有邊之權重（移動成本）相同時，使用廣度優先搜尋尋求最少轉折節點路徑。
3. **課表趕課可行性過濾 (Feasibility Check)**：
   * 計算連續兩堂課程之「最短步行時間 \\(T_{\text{walk}}\\)_」與「課間空堂時間 \\(T_{\text{gap}}\\)_」。
   * 若 \\(T_{\text{walk}} > T_{\text{gap}}\\)，則判定該課表組合存在「趕課不及衝突」，必須將該安排標示為不可行，並記錄衝突地點與時間缺口。

### 4. 輸出結果範例 (Output Example)
```text
=================== 校園最佳路徑與趕課檢查 (F9) ===================
[路徑查詢] 從 TR 研揚大樓 到 MA 管理大樓
- 最短移動路徑：TR 研揚大樓 ➔ 綜合大樓 ➔ MA 管理大樓
- 預估最短步行時間：12 分鐘

[課表趕課可行性檢查案例]
- 課程 A：CS101 (星期二 第 2 節，教室：TR-310，下課時間 10:00)
- 課程 B：MA101 (星期二 第 3 節，教室：MA-101，上課時間 10:10)
- 課間空堂：10 分鐘
- 檢查結果：[不可行 - 趕課不及]
- 說明：教室間最短步行時間為 12 分鐘，大於課間空堂 10 分鐘，系統拒絕此排課組合。
```

### 5. 驗收條件 (Acceptance Criteria)
* 系統必須建置包含至少 **10 個建築物節點** 與 **15 條路線邊** 的校園 Graph 資料結構。
* 使用 Dijkstra 演算法正確計算任意兩地點間的最短步行時間與路徑。
* 能正確將移動時間納入 F2 / F7 課表可行性判斷，對步行時間超過空堂間隔之測試案例精準退件。

## 模組編號：F10 動態事件與課表重新規劃 (Dynamic Event Rescheduling)

### 1. 功能概述
本模組負責處理系統運行過程中所發生的各種動態異動事件（如課程額滿、教師改時間、教室停用與新增必參加活動）。當事件觸發時，系統能自動進行重新規劃與衝堂檢測，並在「儘可能保留原課表有效部分（最小異動原則）」的前提下，自動產生至少一項可行之替代課表方案。若無法產生解，則印出詳細原因。

### 2. 輸入資料規格 (Input)
* `event_type` (Enum)：觸發事件類型（`COURSE_FULL`、`TEACHER_TIME_CHANGE`、`CLASSROOM_UNAVAILABLE`、`STUDENT_NEW_ACTIVITY`）。
* `event_payload` (Object)：動態事件詳細資料：
  * **課程額滿**：額滿課程代號 `course_id`。
  * **教師改時間**：課程代號 `course_id` 與新時間區間 `new_time_slots`。
  * **教室停用**：停用教室代號 `classroom_id` 與停用時間區間。
  * **新增活動**：活動名稱、地點與強制佔用時段 `activity_time_slots`。
* `current_schedule` (Object)：學生目前之已排課表。

### 3. 處理規則與商業邏輯 (Processing Rules)
1. **衝堂與有效性重新檢驗**：
   當輸入任何動態事件時，系統必須將最新異動套入現有課表，重新執行 F2 / F7 / F9 之所有硬性限制（衝堂、學分上限、教室衝突、趕課路徑）驗證。
2. **最小異動重新規劃算法 (Minimal Alteration Rescheduling)**：
   * **保留原則**：鎖定未受該動態事件影響之合法課程與活動，嚴禁無故重排所有課程。
   * **局部替代搜尋**：僅針對受影響之時間缺口或被踢出之課程，搜尋滿足硬性限制之替代選修課或替代教室配置。
3. **無可行方案之診斷與說明**：
   若經重新規劃後依然無法找到同時符合所有硬性約束之替代課表，系統必須輸出詳細之衝突診斷報告，明確標示「因何項不可抗力因素導致無法成功排課」。

### 4. 輸出結果範例 (Output Example)
```text
=================== 動態事件處理與重新規劃報告 (F10) ===================
[觸發事件] 類型：TEACHER_TIME_CHANGE (教師更改上課時間)
- 異動課程：CS101 計算機程式設計
- 原時間：星期一 第 2, 3 節 ➔ 新時間：星期二 第 3, 4 節
------------------------------------------------------------------
[衝突檢測結果] 發現 1 項全新衝堂衝突！
- 衝突地點：星期二 第 3, 4 節 與已選課程 [MA101 微積分] 發生時間衝堂。

[自動重新規劃] 啟動最小異動搜尋替代方案...
- 保留課程：MA101 (微積分)、ENG101 (大一英文) 保持不變。
- 替代方案建議：
  將 CS101 (計算機程式設計) 替換為候選選修課 [CS102 Python 應用] (星期四 第 2, 3 節)。
- 重新規劃後狀態：總學分 18 (符合上限)、0 衝堂、0 趕課不及。
- 狀態：[重新排課成功]
```

### 5. 驗收條件 (Acceptance Criteria)
* 系統必須建立包含以下 4 種動態事件之測試案例並全部通過驗證：
  1. **課程額滿**：學生遭退選後自動改選符合學分與時段之替代課程。
  2. **教師改上課時間**：觸發衝突後能自動保留無關課程並排入替代方案。
  3. **教室臨時停用**：能自動將原教室課程轉移至其他規格與時段相符之空閒教室。
  4. **學生新增必參加活動**：因活動擠壓課表時，能自動重新協調課程組合。
* 重新規劃之結果必須符合「最小異動」原則，不得無故抹除未受影響之課程。
* 當陷入無解情境（例如必修課改時間後無任何替代課且嚴重衝堂）時，系統能精準列出未滿足之具體原因。

## 模組編號：F11 AI 輔助測試與程式品質改善 (AI-Assisted Testing & Quality Refactor)

### 1. 功能概述
本模組規範團隊利用生成式 AI 進行程式碼品質重構、邊界測試案例補充與潛在 Bug 診斷之標準流程。團隊將選擇至少三個核心模組進行雙輪以上的 AI 互動，並建立「AI 建議審查與測試驗證機制」，產出量化的程式品質改善報告，確保所有入庫之程式碼皆經過人類工程師之驗證與測試。

### 2. 輸入資料規格 (Input)
* `selected_modules` (List of Strings)：預計進行 AI 審查改善之 3 個核心模組（例如：`["F2_Conflict_Check", "F7_Schedule_Search", "F9_Path_Planning"]`）。
* `refactoring_prompts` (List of Objects)：針對各模組設計之多輪 Prompt（包含第一輪結構分析/Bug 挖掘，與第二輪重構/測試案例補充）。
* `baseline_code` (String)：進行 AI 改善前之原始 Python 核心程式碼。

### 3. 處理規則與商業邏輯 (Processing Rules)
1. **雙輪 AI 協作審查流程 (Two-Round AI Refinement)**：
   * **第 1 輪 Prompt（結構與 Bug 分析）**：提供原始程式碼與測試案例，要求 AI 診斷潛在邏輯漏洞、時間複雜度瓶頸或邊界條件缺失。
   * **第 2 輪 Prompt（針對性重構與測試）**：根據第一輪 AI 建議與團隊實際測試結果，修正提示詞（例如修正 AI 誤解的業務邏輯），要求 AI 產出重構建議或 unit test 補充。
2. **AI 建議嚴格驗證機制 (Validation Gate)**：
   * 所有 AI 產出之程式碼或測試案例，**嚴禁直接貼入主程式**。
   * 必須經由負責成員執行自動化單元測試（Unit Test）與邏輯推理。
   * 若 AI 建議導致測試失敗或不符規格（如導入全域變數或改變預期邏輯），必須明確標註為 `[AI 錯誤建議]` 並予以拒絕。
3. **品質改善報告彙整 (Quality Report Aggregation)**：
   彙整 3 個模組之重構數據，包含：程式碼可讀性提升、效能改善（如節點數降低）、新增之邊界測試案例數量與正確拒絕 AI 錯誤建議之案例紀錄。
