## 一、作業規範摘要

| 項目 | 規範內容 |
| :--- | :--- |
| 輸入資料 | 活動代號、名稱、日期、開始與結束時間、預計人數、活動類型及場地需求 |

## 二、需求分析

### 2.1 活動資料怎麼存

依迭代 2 的設計（見迭代 2 團隊週報「需求與設計變更」），**活動不另建資料表，存成 `type` 為 `event` 的課程**，放在 `UserData/Courses/{活動代號}.json`。這樣 F2 的衝堂檢查、F3 的課表都能直接處理活動，符合規則 6。

| 規範輸入 | 存放欄位 | 說明 |
| :--- | :--- | :--- |
| 活動代號 | `course_id` | 與課程代號共用同一個命名空間，不得與任何課程或活動重複 |
| 名稱 | `name`（載入後為 `title`） | 不可空白 |
| 日期 | `time_slots[].day` | 該日台北時區 00:00 的 Unix 時間戳（現有資料已採此格式） |
| 開始與結束時間 | `time_slots[].period` | 依 2.2 的節次時間表換算成一或多個節次 |
| 預計人數 | `capacity` | 活動人數上限，≥ 1，且不得超過教室容量 |
| 活動類型 | `activity_type`（新增） | 例如「講座」「社團」「競賽」「迎新」，供查詢篩選；可空白 |
| 場地需求 | `required_equipment`（參考格式已有）與 `classroom` | 設備清單；`classroom` 可由使用者指定，或由系統自動配對 |
| （系統維護） | `credits` = 0、`teacher` = `NPC`、`enrolled_count` | 活動不計學分；報名人數由 F2 加選／退選維護 |

學生報名活動記在學生的 `enrolled_courses`，與選課相同（迭代 2 已將活動檔裡的 `student_ids` 移除，見缺陷 D14）。

### 2.2 時間換算：開始與結束時間 → 節次（組內自訂，待確認）

作業規範用「日期＋開始與結束時間」描述活動，但系統的時段單位是節次。建議採用下表，**活動只要跟某一節的時間有重疊，就佔用該節**：

| 節次 | 時間 | 節次 | 時間 | 節次 | 時間 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 1 | 08:10–09:00 | 5 | 13:10–14:00 | 9 | 17:10–18:00 |
| 2 | 09:10–10:00 | 6 | 14:10–15:00 | a | 18:30–19:20 |
| 3 | 10:10–11:00 | 7 | 15:10–16:00 | b | 19:25–20:15 |
| 4 | 11:10–12:00 | 8 | 16:10–17:00 | c | 20:20–21:10 |

例：10/06 14:00–16:30 → 當天第 5、6、7、8 節。開始時間不得晚於結束時間；完全落在節次以外（例如 12:00–13:00 午休）的活動，回報 `INVALID_TIME_SLOTS`。

### 2.3 規則細化

| 編號 | 規則 | 來源 |
| :--- | :--- | :--- |
| R1 | 活動代號不得與任何課程、活動重複 | 規範（代號唯一）＋自訂 |
| R2 | 自動配對教室時，教室須同時符合：容量 ≥ 預計人數、具備所有需求設備、所有活動節次都沒有被課程或其他活動佔用 | 規範 2、3 |
| R3 | 多間教室符合時，選**容量最小**的一間，避免小活動佔用大教室；容量相同時依教室代號排序 | 自訂 |
| R4 | 找不到教室時，逐項列出未滿足的條件與其最接近的候選（例如「容量 ≥ 150 的教室有 2 間，但都缺少 audio」） | 規範 5 |
| R5 | 報名活動走 F2 的加選流程：額滿（`enrolled_count` = `capacity`）時拒絕，並檢查與已選課程、其他活動的衝突 | 規範 4、6 |
| R6 | 取消活動：已有學生報名時須先確認；確認後自動為所有報名學生退選，再刪除活動並釋放教室 | 自訂（對應 F1「先退選再刪除」） |
| R7 | 修改活動時間、人數或設備：重新檢查原教室是否仍符合；不符合時重新配對，新配對失敗則維持原狀並回報原因 | 自訂 |
| R8 | 預計人數不得低於目前報名人數 | 自訂（對應 F1 修改課程的同一規則） |

## 三、介面設計

所有函式維持 F1–F3 的慣例：**純函式**，第一個參數是 `database`，回傳 `(ok, code, ...)`，不印出文字、不讀寫檔案；存檔由 `CourseDataManager` 包裝。

### 3.1 函式清單

| 函式 | 輸入 | 回傳 | 狀態 |
| :--- | :--- | :--- | :--- |
| `FindAvailableClassrooms(database, timeSlots, minCapacity=1, requiredEquipment=None)` | 時段、最低容量、設備需求 | `(ok, code, classrooms)`；`code` 為 `OK` 或 `NO_AVAILABLE_ROOM` | 已有初版 |
| `ExplainUnavailable(database, timeSlots, minCapacity, requiredEquipment)` | 同上 | `[未滿足條件, ...]`，例如 `{"reason": "MISSING_EQUIPMENT", "equipment": ["audio"], "candidates": 2}` | 待實作（R4） |
| `TimeRangeToSlots(dateTimestamp, startTime, endTime)` | 日期時間戳、`"HH:MM"` 開始與結束時間 | `(ok, code, timeSlots)` | 待實作（2.2） |
| `AddActivity(database, activity)` | 活動字典；`classroom_id` 可省略 | `(ok, code, classroomId)` | 已有初版；需改為可自動配對（R2、R3） |
| `UpdateActivity(database, activityId, changes)` | 活動代號、異動欄位 | `(ok, code)` | 待實作（R7、R8） |
| `CancelActivity(database, activityId)` | 活動代號 | `(ok, code, droppedStudentIds)` | 待實作（R6） |
| `QueryActivities(database, activityId=None, date=None, activityType=None, hasSeats=None)` | 篩選條件（AND） | 活動清單 | 待實作 |
| 報名／取消報名 | 學號、活動代號 | 共用 F2 的 `EnrollCourse`、`DropCourse` | 已完成 |

### 3.2 錯誤碼

沿用 `Constants.py` 既有的錯誤碼，不另訂新碼：

| 錯誤碼 | 使用情境 |
| :--- | :--- |
| `DUPLICATE_ID` | 活動代號已被課程或活動使用（R1） |
| `INVALID_FIELD`、`INVALID_TIME_SLOTS` | 欄位缺漏、時間格式錯誤或不在任何節次內 |
| `CLASSROOM_NOT_FOUND` | 指定的教室不存在 |
| `ROOM_CONFLICT` | 指定的教室在活動時段已被佔用（與 F2 同一套檢查） |
| `CAPACITY_EXCEEDS_ROOM` | 預計人數超過指定教室的容量 |
| `NO_AVAILABLE_ROOM` | 自動配對找不到合適教室（搭配 `ExplainUnavailable` 列出原因） |
| `ACTIVITY_NOT_FOUND` | 修改、取消、查詢時找不到活動 |
| `COURSE_FULL`、`ACTIVITY_CONFLICT` | 報名時活動額滿或撞時段（F2） |

### 3.3 CLI 規劃

| 選單 | 功能 | 對應函式 |
| :--- | :--- | :--- |
| 新增活動 | 輸入代號、名稱、日期、開始／結束時間、預計人數、類型、設備需求；可指定教室或讓系統配對 | `TimeRangeToSlots` → `AddActivity` |
| 查詢活動 | 依代號、日期、類型、是否有名額查詢，顯示教室、時間與報名人數 | `QueryActivities` |
| 修改活動 | 同 F1 修改課程，Enter 表示不修改 | `UpdateActivity` |
| 取消活動 | 顯示報名人數並確認 | `CancelActivity` |
| 報名／取消報名 | 已整合在選單 15、16 | `EnrollCourse`、`DropCourse` |

輸出範例（找不到教室；教室與課程名稱僅為示意）：

```text
[錯誤] 活動建立失敗：沒有符合條件的教室
未滿足的條件：
  - 容量至少 150 人：符合的教室有 2 間（IB-101、IB-201）
  - 需要設備 audio：上述 2 間中只有 IB-101 具備
  - 時段 2026-10-06（星期二）第 5、6 節：IB-101 已排定 CS303 作業系統
```

## 四、與其他功能的關係

| 功能 | 關係 |
| :--- | :--- |
| F1 | 刪除教室時，被活動使用中的教室同樣不得刪除（現有 `DeleteClassroom` 已包含活動） |
| F2 | 教室衝堂、報名衝突、額滿檢查全部共用 `ConflictChecker`，不另寫一套 |
| F3 | 學生報名的活動會依日期換算成星期，顯示在個人課表上並標示為活動 |
| F6 | 活動以 ID 分檔存在 `Courses/`，讀寫與容錯沿用 `StorageManager` |

## 五、驗收測試規劃（迭代 3 實作時先寫測試）

規範要求至少 10 項活動。現有資料有 3 項（ACT01–ACT03），迭代 3 須在 `TestDriver/TestInput/Courses` 補到至少 10 項，並涵蓋下列情境：

| 編號 | 情境 | 預期結果 |
| :--- | :--- | :--- |
| A01 | 新增活動、自動配對教室 | 成功，選中容量最小且符合設備的空教室 |
| A02 | 多人報名同一活動直到額滿 | 前面成功、額滿後回報 `COURSE_FULL` |
| A03 | 報名時與已選課程撞時段 | `ACTIVITY_CONFLICT` |
| A04 | 取消已有學生報名的活動 | 報名學生全部退選、教室時段釋放，同時段可再配置其他活動 |
| A05 | 指定教室但教室已被課程佔用 | `ROOM_CONFLICT` |
| A06 | 找不到合適教室 | `NO_AVAILABLE_ROOM`，並列出每一項未滿足的條件 |
| A07 | 預計人數超過教室容量 | `CAPACITY_EXCEEDS_ROOM` |
| A08 | 修改活動時間後原教室撞期 | 自動改配其他教室；無教室可改時維持原狀 |
| A09 | 開始時間晚於結束時間、時間不在任何節次 | `INVALID_TIME_SLOTS` |
| A10 | 依日期、類型查詢活動 | 只列出符合條件的活動與目前報名人數 |
